# 分片告警合并查询服务

值班员排障时从三个告警分片查询最近 N 条告警的 FastAPI 服务。三个分片各持一份
**只追加**的 SQLite 库；查询只看查询开始时已提交的数据，按
`(timestamp, id)` 倒序跨分片合并，并在给定查询时限内尽早返回。

## 1. 需求与实现对照

| 需求 | 实现 |
| --- | --- |
| FastAPI 接收 N 和查询时限 | `GET /alerts/latest?n=&timeout=`，参数经 Pydantic 校验（n≥1，timeout>0） |
| 三个分片各一份 SQLite、只追加 | `app/shard.py`，每分片一个 `shard_{i}.db`；写入只有 `INSERT` |
| 告警编号单实例全局唯一 | 录入前跨分片查重，编号已入库返回 409；同号并发在 `ShardRegistry` 内串行，只允许一条落盘（见下） |
| 只看查询开始时已提交的告警 | 每个查询用独立连接开启只读事务并立即发一次 SELECT，把 WAL 读快照钉在开始时刻；查询中的补报对本查询不可见 |
| 按时间和唯一编号倒序合并 | 排序键 `(timestamp DESC, id DESC)`，同时间戳由 id 决胜 |
| 分片先给最新排序键，再给明细 | 合并第一阶段并行 `head()` 取各分片最新 key；第二阶段才按需读明细 |
| 每批最多读 20 条 | `ALERT_BATCH_SIZE=20`，`read_batch` 以行值游标 `(timestamp,id) < cursor` 翻批 |
| 确认前 N 条立即返回 | 惰性 k 路归并：只有“全局最大上界”属主缓冲为空时才读批；确认够 N 条立刻返回，较旧分片明细不读 |
| 读完仍不足 N 返回全部 | 全部分片耗尽返回 `status=exhausted` 和全部可见告警 |
| 到时补不齐返回最长有序前缀并指出阻塞分片 | `status=timeout`、`complete=false`，`blockers` 给出分片号、阶段（head/batch）、原因、耗时 |
| Docker Compose 启动，/docs 录入查询 | `Dockerfile` + `docker-compose.yml`；启动后访问 `http://localhost:8000/docs` |
| 样例可给明细读取加延迟 | `ALERT_SHARD_DELAYS="0,0,0.4"`，延迟在 asyncio 层、可被时限即时取消（只加在明细批次，head 不延迟） |

### 单实例告警录入（修复说明）

问题：编号唯一性此前只由各分片自己的 `PRIMARY KEY` 保证，同一编号补报到
**两个不同分片**时两边都能插入成功，查询就会看到两条。现在由
`ShardRegistry.append`（`app/main.py`）统一协调：

1. **跨分片查重**：写入前逐个分片用短命只读连接查该编号，任一分片已有即
   返回 `409`。旧库中已经存在的重号不受影响，照常可查（查询不做去重）。
2. **同号并发串行**：进程内维护 `编号 -> 在途录入 Task`。后来到达的同号请求
   不另起写入，而是 join 同一个 Task：
   - 原任务已提交 -> 后来者 `409`；始终只有一条落盘；
   - 原任务**确认未提交**（例如等锁时被取消、写入明确失败）-> 后来者继续录入。
3. **取消语义**：录入在独立 Task 中执行，请求协程被取消（客户端断开、超时）
   不会取消写入。即便录入 Task 自身被取消，只要 `INSERT` 线程已启动，也会
   等线程给出确定结果再结束；未提交返回 `503`（明确可重试），已提交则同号
   重试得到 `409`。绝不出现“报错但已落盘却查不到 / 重复落盘”。
4. **分片级写锁隔离**：每个分片一把写锁，等待某一片的 SQLite 写锁时，其它
   分片仍可录入不同编号。查重走 WAL 只读连接，不会被待写事务挡住。

### 合并算法要点（`app/merge.py`）

每个分片维护一个“剩余数据严格上界” `upper`：

- `head` 返回的 key 是初始上界；
- 读到一批后，上界是缓冲首条 key；缓冲耗尽但可能还有数据时，上界退化为上一批
  最后一条 key。

每轮取所有活动分片中上界最大的属主：

1. 属主缓冲有数据 → 其首条已被其它分片的上界夹住，**可确认输出**，不需要读任何
   较旧分片；
2. 属主缓冲为空 → 必须先读它的下一批，此时其它分片的行一条都不能提前输出
   （属主下一批可能存在更靠前的行）；
3. 读批前/等待中检查时限，超时即返回已确认的最长有序前缀，并把该属主记入
   `blockers`。

### 快照隔离的关键坑

Python 3.11 的 `sqlite3` 遗留隔离模式下，普通 `SELECT` 运行在 autocommit 中
（`in_transaction=False`），每次读都取最新快照，单独 `BEGIN` 而不立刻读也不会
固定视图。因此 `ShardSnapshot` 必须 **先 `BEGIN`，紧接着执行一次 `SELECT`**，
WAL 读快照才会被钉住（已用最小复现和测试验证）。

## 2. 目录结构

```
app/
  config.py     # 环境变量配置（分片数、库目录、延迟、批大小、默认时限）
  shard.py      # SQLite 只追加写入 + 只读快照（head / read_batch）+ 跨分片查重
  main.py       # FastAPI 路由、单实例录入协调（查重 / 同号串行 / 取消语义）
  merge.py      # 惰性 k 路归并、时限控制、阻塞分片识别
  models.py     # 请求/响应模型
scripts/
  seed.py       # 幂等样例数据（68 条，含同时间戳决胜与慢分片专属新告警）
tests/          # 24 个 pytest：合并、分页、快照隔离、超时、API、查询中补报、录入协调
Dockerfile
docker-compose.yml
```

## 3. 启动方式

### Docker Compose（交付主路径）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000/docs
```

compose 中分片 2 每批明细读取延迟 0.4s，用于演示超时。数据保存在命名卷
`alert-data`；清空数据：`docker compose down -v`。

### 本地直接运行（无 Docker 环境时的等价方式）

```bash
pip install -r requirements.txt
export ALERT_DB_DIR=./data ALERT_SHARD_DELAYS="0,0,0.4"
python scripts/seed.py
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## 4. /docs 操作说明

1. `POST /alerts/{shard_id}`：手工指定 id 录入；`POST /alerts/{shard_id}/auto`
   自动生成 UUID，适合在 /docs 里做补报实验。
   手工录入时把同一 `id` 再发到另一个分片会返回 `409`（编号全局唯一）；
   写入未完成（已确认未提交）返回 `503`，可用同号重试。
2. `GET /alerts/latest`：填 `n`（条数）与 `timeout`（秒）。
3. 响应字段：
   - `alerts` / `count`：已确认的有序结果（超时时为最长有序前缀）；
   - `status`：`complete`（拿满 N）/ `exhausted`（全库不足 N）/ `timeout`；
   - `shards[].head_key`：各分片本次可见的最新排序键；
     `shards[].batches_read`：实际读取的明细批次数（head 不计）；
   - `blockers`：超时场景下挡住后续的分片与阶段。

- 同号先写分片 0、再写分片 1/2：后者均 409，全库仅 1 行；
- 同号在 3 个分片并发提交：恰好 1 个 200、2 个 409，落盘 1 行；

- 请求协程在写入中途被取消：原写入仍落盘；同号重试在写入结束前挂起等待，
  结束后返回 409，全库仅 1 行；
- 等写锁时录入 Task 被取消（写入未开始）：返回 503，同名重试可成功录入 1 行；
- 录入 Task 在写入中途被取消：任务等写入线程落定，明确报成功；同号重试 409；
- 写入明确失败（未提交）：返回 503，恢复后同名重试成功；
- 分片 0 被外部 SQLite 写锁占住：分片 0 写入阻塞，分片 1/2 录入不同编号
  在 2s 内完成；释放后分片 0 写入成功；
- 旧库跨分片已存在同号：查询仍返回两条（不去重），再次录入返回 409。

### 真实 HTTP 实测（uvicorn + 空库，分片 2 延迟 0.4s/批）

- 先向分片 0 写 `demo-1`（200），再向分片 1 写同号：`409 告警编号已存在`；
  查询 `demo-1` 仅 1 条。
- 8 个并发请求把 `demo-race` 打到 3 个分片：1 个 200、7 个 409，查询仅 1 条。
- 30 个不同编号跨 3 分片并发：全部 200，总耗时 253ms；`n=5,timeout=5`
  正常合并返回（慢分片 1 批约 0.4s）。
- 外部连接在分片 0 上 `BEGIN IMMEDIATE` 持锁：发往分片 0 的写入一直等待
  （锁释放后 200）；这期间分片 1/2 录入不同编号 34ms 完成。
- 直接向分片 1/2 插入旧库重号 `legacy-dup`：查询返回 2 条；再经 API 录入
  该编号返回 409（对分片 1 本身、分片 0 均如此）。
- 取消后重试的确定性另用 90 轮随机时序脚本对 `ShardRegistry` 压测：任意时刻
  取消请求协程或录入 Task，最终每编号恰好 1 行，重试只得到 200/409/503，
  无挂起、无重复。
- `/docs` 返回 200；参数非法返回 422；重复 id 写入返回 409。

## 6. 未完成项 / 限制

1. **本环境没有 Docker 守护进程**，`docker compose up --build` 未在本机实跑；
   Dockerfile/compose 已按标准 Python 3.11-slim 镜像编写，需在有 Docker 的
   环境验证一次。
2. **单实例保证**：唯一性与在途协调是进程内的（asyncio Task + 字典）。
   多 worker（`uvicorn --workers>1`）或多副本共享同一数据卷时，跨进程同号
   并发仍可能各写一个分片。要做到跨进程唯一，需引入文件锁 / SQLite 全局
   唯一的编号表 / 外部协调服务；本需求限定“单实例”，当前实现未覆盖。
3. 阻塞分片目前报告“全局最大上界属主”这一直接阻塞者；若需要把所有在途未返回
   的分片都列出，可在后续版本扩展（协议上属主才是有序前缀的硬阻塞）。
4. 人工延迟是演示用的同步等待模拟，真实分片应替换为网络/远程 DB 客户端；
   合并引擎与分片接口未耦合，替换 `ShardSnapshot` 实现即可。
5. 未做鉴权与多租户隔离，按内部运维工具假设部署在可信网络。
6. 测试使用 FastAPI `TestClient`（基于 httpx 的同步封装，有一条 starlette
   弃用告警，不影响功能）。
